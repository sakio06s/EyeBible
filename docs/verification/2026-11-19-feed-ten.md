## 今日經文的原因與修正
正式資料 endpoint 已回傳 **2026-11-19，阿摩司書 9:7–15**，排程成功；但測試分支內的 JSON 停在 11 月 18 日。標準 Vercel 測試網址改由同源 Node API 讀 main 中排程更新的已驗證 JSON，不再讀凍結分支的舊資料。固定來源、日期格式、1 MiB 大小上限、8 秒逾時；沒有任意 URL 代理或憑證轉傳。正式站與本機仍走原靜態每日檔案。

測試涵蓋 API 路徑與輸入驗證，以及 Chromium/WebKit 在靜態分支資料過期時仍載入今天、簽到記錄於今天、來源離線時保留已存標註、新瀏覽器離線時回到部署內最近可用正式經文。舊經文不會改標為今天，也不會修改原日期紀錄。

公開正式 JSON 已用 HTTP 實際確認。工作區 Node 直連外網在此執行環境的 proxy 設定下逾時，沒有把它當作 Vercel runtime 驗收成功；Node handler 的資料驗證與瀏覽器流程採可重現 fixtures。部署後仍需使用者重新整理確認實際日期。

## 小組資料庫與介面
- 真實 PostgreSQL 17：私人／小組／匿名／他組權限、30 天邀請、封鎖與換碼、操作收據、tombstone、並行入組、歷史分頁全部保留原測試。
- 新測試：不限制天數、每頁十筆、舊留言因新回覆優先、回覆阿們及舊重試不逆轉新選擇、刪除回覆後不能反應、合法本組父文章搭配他組回覆 ID 仍被拒絕。
- Chromium/WebKit：十筆首屏、內部滑動自動加十筆、回覆阿們、透明 tap highlight、下方頭像可到達。邀請「是／否」、草稿、資料隔離、歷史與經文標註回歸仍通過。
- 一次獨立完整審查找出三項重要問題：刷新和續載互相覆蓋；輸入時續載被延後與鍵盤焦點丟失；畫面與暫存模型不同時阿們反向操作。皆加入失敗重現，再於同一次修正階段完成。
- 修正後測試確認：背景刷新不把二十筆退回十筆；手動刷新不接上舊游標回應；輸入中的 DOM、文字及選取位置保留，下一頁照常加入；鍵盤操作有明確焦點；阿們依畫面上的按下狀態決定意圖。
- 審查另列來源離線時的新訪客 fallback 為輕微；因本次核心要求就是經文可載入，提升為必須修正，已驗證。沒有延期的審查項目。

## 實作決策與取捨
1. 有任何未刪回覆的貼文都優先，再依最近回覆時間；無回覆依發佈時間。這是對「有人回覆的留言置頂」的具體解讀，較舊但有討論的貼文可能排在最新未回覆貼文前。
2. 使用者明確選擇留言區內捲動，單次十筆、頭像在下方；不需要讀完全部歷史才能到頭像。
3. 新牆使用 `group_feed` 的回覆狀態／活動時間／ID 游標。舊 `group_read` recent 保留相容模式；日期足跡仍二十筆一頁，避免改動與本次無關的既有日期介面。舊客戶端需重新整理才能使用新牆規則。
4. 刷新與續載協調為同一序列，保留待處理的向下滑動，並綁定帳號／小組世代。可能多等一次已在途的請求，但不再互相覆蓋或把舊組意圖帶到新組。
5. 續載只增加新 DOM，不重建正在輸入的控制。背景排序變化可等輸入安全時再重畫，換來草稿與游標穩定。阿們從畫面 `aria-pressed` 讀取意圖，伺服器仍驗證成員與文章／回覆並保存操作收據。
6. 使用 preview-only 同源 API，避免需要改正式站 CORS。自訂測試網域不在這次路由範圍，若新增需另外設定。
7. 回覆阿們及新排序需重跑最新版 `cloud/groups.sql`，新增表格、排序欄位與 RPC 並回填排序資訊；原有文字、小組、成員、邀請碼、簽到和私人資料不刪除。沒有已登入的 Supabase 管理工具，不能替使用者執行 migration 或宣稱已生效。
8. 保留草稿 PR 與正式主站，更新測試版。先驗證新 SQL 和今日經文，再繼續正式上線驗收。
