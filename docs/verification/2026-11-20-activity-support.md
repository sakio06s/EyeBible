# 最新互動、緊湊按鈕與站內問題回報 — v0.15.1

## 行為與資料

小組互動三個按鈕靠左依內容寬度排列，間距12px；阿們的數字和回覆使用一般文字空格，不保留尾端假空白。兩者字體13px、同一基線、42px點按高度，愛心14px。最新要求的可見文字緊湊等距優先於早期推定的反應按鈕固定寬度：數字位數改變可讓後面的按鈕橫向自然移動，垂直捲動與DOM節點保持。99→100測試保留頁面／留言流位置斷言。

直接留言按鈕是「分享」，仍以kind=group儲存在個人足跡，可重載查看；不附上經文。SQL依max(建立時間,最新回覆時間)與ID降序排序，游標與索引一致，因此新直接留言會超過較舊的有回覆留言。自己送出確認後定位到固定發文列下方。我的小組名稱使用16px、400字重。

已取消Email API與寄信服務設定。一般使用者的問題回報送到Supabase；全平台管理者從同一入口開啟問題列表，看到誰／日期／內容，並可標記已處理或刪除。三處新回報提醒：首頁、頭像、我的設定。開啟的列表頁標成已讀，每頁20則；首次登入、回到瀏覽器、首頁／設定切換及小組下拉更新觸發讀取，沒有輪詢。

回報／管理者／已讀表啟用RLS並拒絕一般角色直讀，僅授權兩個帶身份檢查的RPC。作者取auth.uid；組長不是全平台管理者。操作ID去重，交易鎖保證每帳號10分鐘最多5筆，同ID重試不增加計數。刪除留下伺服器墓碑。公開SQL只含管理者信箱占位符，私有填妥版不在儲存庫；管理者種子只接受已確認Email且有相符已驗證Google身份的帳號。

## 驗證及審查

隔離Postgres17測試先觀察舊排序與缺少回報RPC失敗，再驗證新留言超過舊回覆、游標／歷史／私密邊界、未讀與列表、處理／刪除、UUID去重、偽造作者與持久限流。六個並發回報只接受五個。未確認Email／非Google身份的管理者設定會回滾；EXPLAIN證明最新互動查詢可依索引排序。

Chromium與WebKit使用實際隔離Postgres驗證一般回報者／管理者、三處提醒、提供者與日期、20→23筆分頁、處理／刪除、換帳號清除、舊帳號多頁讀取停止、關閉列表停止後續讀取、鍵盤開窗與焦點保持。另以SDK fixtures驗證各帳號Bearer；活動／分享fixtures驗證超過十篇舊回覆時新留言仍第一、送出定位與足跡重載。按鈕新增可見文字間距測試，在舊尾端空白下先失敗，再修正。

一輪獨立整體審查發現多頁讀取換帳號時可能繼續發出RPC、管理者種子未檢查Email驗證。已用失敗測試補上每次await前後的帳號／請求／開窗檢查與已驗證Google身份條件。同一輪修正開窗／重繪焦點與排序索引。下拉更新fixture原先把最新回覆時間設成建立時間，導致排序更新後取到沒有回覆數的列；已把fixture更新為符合真實payload的活動時間，完整下拉互動測試通過。

最終回歸：2個隔離資料庫腳本＋17個Node測試腳本全數通過（包含48項小組邊界案例、Chromium／WebKit、標註、每日經文、跨裝置與SDK登入隔離）。`git diff --check`通過；追蹤來源未包含私有管理者信箱。

## 啟用界線

本次只部署預覽分支，沒有修改main或執行真實Supabase SQL。測試通過不代表線上migration已啟用。需要管理者在現有專案SQL Editor執行一次私有升級檔，然後重新整理預覽；該檔同時啟用站內回報與更新小組排序。現有資料不刪除。無需Email供應商、SMTP或寄信金鑰。實體iPhone、真實Google登入與正式Supabase權限仍由實際帳號驗收。
